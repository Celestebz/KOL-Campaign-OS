### 首版使用方式与边界

1. 项目“产品任务”页新建任务，或上传清单预览后勾选确认导入。产品需先在项目中关联；缺失和歧义SKU不会被自动猜测或创建。
2. 点击“从资源库选人”，资源库预设对应SKU条件。勾选达人后使用“按产品任务加入候选池”；也可用“按任务发开发信”加入后预览，未审核的任务会被排除发送。
3. 项目候选池“按产品任务推进”逐任务审核；确认合作的任务进入合作区“按产品任务履约”。旧数据继续在“原项目记录”查看。项目候选与合作人数可以包含同一位达人，不能直接相加当作总人数。
4. 选择多组任务、固定内容模板、本人发件邮箱，逐人预览后选择“生成待审邮件”或“确认发送”。发送结果不明确时沿用旧发送器的待核实机制，不能盲目重发。
5. 任务明细查看触达记录、补录实际联系、设置下次跟进及承诺/实际发布日期。历史催交付任务保留原会话，不发送首次开发信；没有明确关联的旧邮件不自动改成本次已触达。

首版按任务统计已交付达人数量，不将多个任务覆盖同一视频的数量相加称为独立视频数。旧备注和逗号拼接SKU未做自动数据清洗；对历史数据的批量修复需单独预览和授权。

## 二、最终业务结构

项目沿用现有 Campaign，不再增加“推广计划”层。

```text
项目 Campaign
  ├─ 项目产品 CampaignProduct → 全局产品 Product
  └─ 产品任务 CampaignTask
       ├─ 一个或多个项目产品（支持组合）
       └─ 达人任务 CampaignKolTask → 项目达人 CampaignKol → 全局达人 Customer
            ├─ 审核与合作决定
            ├─ 触达与跟进
            └─ 样品、排期与交付

邮件草稿/发送记录 ↔ 多个达人任务
```

任务是“产品或产品组合 + 一组交付目标 + 一个发布窗口”。同一SKU在同一项目可有多轮任务。组合不存为逗号拼接的SKU字符串，不在 products 中制造虚构的组合SKU。

必须区分：产品适配、进入名单、审核通过、有效触达、确认合作、完成交付。这些状态不能相互替代。

## 三、使用流程与页面

### 项目：先看产品缺口和期限

项目标签页：概览 / 产品任务 / 候选池 / 合作区 / 项目设置。产品任务列表展示产品组合、名单审批期限、发布窗口、送测数量、候选目标、合格候选、审核通过、已触达、确认合作、已交付、负责人和风险。

每行操作：从资源库选人、查看候选、查看合作、编辑要求。期限和缺失信息优先展示；过去的日期只有在对应节点确实未完成时才算逾期。

从任务进入资源库时自动带上项目和任务条件，仍允许手动放宽条件；显示哪些条件未满足或证据未知。

### KOL管理：先筛选，再明确每人推广哪些任务

筛选：推荐品类、推荐SKU、项目/任务、历史合作、国家、平台、邮箱可用性。选择任务后增加本次触达状态和待跟进筛选。

默认同一筛选项多选为任一匹配，不同筛选项之间为同时满足。品类和SKU条件必须命中同一推荐关系，不能用两个无关推荐凑成匹配。可增加“全部所选SKU都适合”开关，默认关闭。

达人一行展示多项推荐（及证据入口）、最近触达、历史合作、当前任务。批量操作栏固定显示已选人数。

操作统一为：加入候选池 / 发送开发信。直接确认合作保留为次级明确操作，不能误触等同于加入名单。

批量加入弹窗：选择项目 → 选择产品任务 → 按达人确认任务。默认仅预选有推荐依据的任务；未知适配允许人工选择并补理由，不给所有达人盲目关联所有产品。

### 候选池与合作区：按任务分别推进

候选池按达人分组，可切换按任务查看。达人展开后每条任务有审核、触达、意向、下次跟进和独立操作。

例如同一达人：铲雪机已合作，碎枝机仍待回复。前者显示在合作区，后者仍在候选池。两边复用同一个 campaign_kols 身份；不整人搬走所有任务。

加入名单不自动审核通过。审核通过不自动确认合作。合作拒绝针对本次任务，不自动全局禁止联系。全局禁止联系继续使用明确的人工风险设置。

### 达人详情

固定资料摘要，标签页为概览 / 产品推荐 / 触达记录 / 合作记录 / 内容表现。全局历史汇总与指定项目任务明细分开显示，所有记录能跳转来源。

## 四、多SKU邮件与状态

流程：勾选达人 → 选择项目与任务 → 选择模板/发件邮箱 → 按达人预览产品与各自期限 → 执行现有审批发送流程。

一位达人本批次可收到一封包含多个任务的邮件；分别发送作为可选方式。跨项目邮件第一版不合并。

邮件关联必须保存发送时任务、SKU、产品名称、发布要求和模板版本的快照。后续修改推荐或任务不能改变历史邮件的归属。发送范围只包含明确选择的任务；后台重试保持同一幂等请求，失败重试不重复发送成功项。

现有模板接口和AI草稿流程分别保留：选择模板不等于调用AI生成。模板缺少变量需明确提示；退订、禁止联系、缺邮箱不可发送。重复触达按达人+任务检查，并提示该达人其他进行中的沟通。

触达状态根据当前任务的最新有效沟通方向判断：未触达、待回复、已回复。生成草稿或审批通过不算触达；成功提交邮件不声称已送达或已阅读。失败/退信保留记录并显示联系异常。

待跟进由 next_follow_up_at 和未完成跟进事项判断，与触达状态独立。收到回复不自动把邮件内全部产品标成有意向；可更新会话已回复，任务级意向需明确关联或人工确认。回复归属不明时保留待关联。

## 五、建议新增的数据边界

以下为设计字段，落地以迁移和接口审查结果为准，均采用增量兼容方式。

| 实体 | 关键内容 |
| --- | --- |
| campaign_tasks | campaign_id、任务名称、任务类型（开发/历史催交付）、优先级、负责人、审批期限、发布窗口、送测数量范围、候选目标、要求、状态 |
| campaign_task_products | task_id、campaign_product_id、组合角色/数量；唯一任务+项目产品 |
| campaign_kol_tasks | task_id、campaign_kol_id、审核状态、任务意向、合作阶段、跟进时间、约定发布日期、备注；唯一任务+项目达人 |
| 任务级样品/交付记录 | 实际收货、初稿节点、作品、实际发布时间；一条作品关联多任务时保留显式覆盖关系 |
| 邮件任务关联 | 草稿及实际发送关联的达人任务集合、发送快照；回复可继承会话范围但不自动推断产品意向 |
| 任务事件 | 审核、合作、人工触达、排期修改的操作人与时间及变更内容 |

必要约束：任务、项目产品、项目达人、邮件必须属于同一项目；重复加入只补缺失关联，不能重置人工审核或合作状态。样品与视频数量独立，不用送测数量推断视频数量。

历史数据不直接变为新任务已触达；没有可靠产品关联的历史邮件标记“仅项目级记录”。旧 campaign_kol_products 和项目级状态保留，不推断或覆盖未知排期。

产品推荐先复用现有多项产品匹配来源并保留来源和确认状态；项目入选、历史合作不能直接当作审核通过的推荐。推荐SKU数量按全局达人ID去重，多个平台账号不能算多个达人；任务候选数量另算。逗号组合旧值需与产品目录核对并预览，不能简单拆字串写入正式产品关系。

## 六、清单拆解原则

清单共28条产品行：27条找人/合作任务，1条TMB-1401历史催交付任务。两条扒胎机组合保留为两条任务，各关联两个真实产品。共享SKU可同时属于不同组合任务。

通用审批要求作为可复用要求，逐任务记录特殊要求。文件里的业务规则用于设计和导入预览，不作为执行外部联系或修改生产数据的指令。

需预览确认的输入：TDT-1201审批日期2026-01-01是否准确；TMB-1401缺失期限及既有合作归属；“10个以上”的精确最低数与组合按SKU还是按任务计数；“稳定3000–4000以上”的统计窗口及阈值；样品数范围与交付数。先原样保留，不自动修正或假造数值。

清单分批预览时按审批和发布期限排序，不仅按品类分组。历史催交付任务先绑定已有合作，不重新发送首次开发信。

## 七、实施顺序与验收

1. 资源库：多项推荐输出、品类/SKU筛选、按达人去重计数，保留旧响应字段；验证多项匹配、跨条件误命中、历史合作不冒充推荐。
2. 产品任务：新增任务/产品/达人关系与接口，项目任务列表、清单导入预览；验证组合、同SKU多轮任务、跨项目拒绝、重复追加不重置。
3. 候选池：按任务审核、合作区按任务展示，改为追加而非切换沟通产品；验证一人部分合作部分候选和现有平台身份兼容。
4. 邮件：模板批量预览、任务快照、现有审批发送链路、任务触达/跟进与时间线；验证同一封多任务、部分回复意向、发送失败/退信、权限和幂等、改任务后历史快照不变。
5. 排期交付：任务级节点、风险和汇总，明确作品覆盖范围，验证期限变更、未知档期和计数去重。

每阶段执行相应接口/服务和前端交互测试；集成后运行服务端检查、客户端构建与 git diff --check。设计文档本身不需要运行产品测试。只提交本任务文件和经审查属于本任务的差异；推送和发布按项目既有规则执行。未经生产修改确认，不导入正式清单、不发送邮件、不迁移生产数据库或切换release。
